# Plan 02-01 — Bring Public Contracts into Conformance

Status: Proposed; not approved for implementation.

## Purpose

Bring runtime behaviour, locally maintained product claims, production
configuration authority, and resilient verified delivery into conformance with
the intended architecture in ADR-0002, ADR-0003, ADR-0004, ADR-0006, ADR-0007,
and ADR-0009 after those records have completed human review and acceptance.
ADR-0005 and ADR-0008 provide the governing Worker-first route-exposure and
subordinate static-serving context. This eight-slice plan records current
divergence separately from the ADRs; it does not authorise runtime
implementation, tests, deployment, or operational changes.

## Preconditions and Boundaries

- The relevant ADRs must complete human review and acceptance before runtime
  conformance work begins. No agent may mark them Accepted.
- This plan must be approved as an implementation work packet before any slice
  starts.
- Each slice is a meaningful work-unit and requires its own verification and
  review checkpoint.
- Where an endpoint schema, failure contract, cache mechanism, or other public
  behaviour still needs a concrete specification or decision, stop at that
  specification/decision checkpoint rather than choosing a mechanism during
  implementation.
- The repository has no general code-quality CI arbiter and no tracked runtime
  test harness. Introducing or changing a test harness, dependency, build
  invocation, CI workflow, deployment workflow, service wrapper, or environment
  setup requires a separate approved mechanism change.
- Changes to `.gsd/gate.sh`, CI, test harnesses, builds, deployment, or
  environment remain checkpoints unless separately approved. Push, PR creation,
  merge, publish, release, deployment, and ADR acceptance remain prohibited
  without their exact approval gates.

## Current Conformance Evidence

- Negotiated root responses select HTML or installer bytes from request headers,
  while the HTML response is publicly cacheable without an explicit contract
  that partitions every representation-selecting input or avoids shared caching.
- Markdown fallback construction incorporates exception detail into a string
  later assigned to `innerHTML`.
- `/trust.json` publishes experimental policy claims and does not define a
  versioned schema or complete unknown/degraded and failure semantics.
- Release resolution can retain per-artefact fallback URLs while attaching a
  release tag resolved from a different path, so one coherent release-backed set
  is not guaranteed.
- `/llms.txt`, route descriptions, trust/provenance prose, and locally maintained
  frontend claims have not yet received a complete source/evidence mapping and
  drift audit against canonical upstream product truth.
- Repository defaults name the canonical production upstream, but runtime
  configuration permits overrides; actual deployed Cloudflare values and the
  authorised emergency-override/reconciliation path have not yet been audited
  against the intended production-authority invariant.
- Cloudflare's current Assets configuration does not select Worker-first routing,
  so a matching packaged file can be served before `src/index.js` classifies the
  request. Effective routing therefore diverges from ADR-0005 and ADR-0008's
  intended bounded-namespace architecture and permits file presence to shadow
  Worker policy.

These observations are planning inputs, not amendments to the intended
architecture recorded by the ADRs.

## Future Slice A — Negotiated-root cache partitioning and tests

### Scope

- Define the concrete cache contract for every request input used to select the
  root representation.
- After that contract is approved, make `/` either partition shared cache entries
  across all representation-selecting inputs or avoid shared caching for the
  negotiated variants.
- Preserve browser HTML, CLI installer, and deterministic `/install.sh`
  behaviour.
- Add focused regression coverage for both request orders through the applicable
  shared-cache path.

### Expected outputs

- An approved cache contract or specification naming the representation inputs
  and selected strategy.
- A bounded Worker change implementing that strategy.
- Regression tests proving HTML is never reused for CLI installer requests and
  installer bytes are never reused for browser HTML requests.

### Verification

- Exercise browser and representative CLI root requests in both cache-warming
  orders and compare media type and body class.
- Exercise `/install.sh` with browser-like and CLI-like headers and confirm the
  same installer representation.
- Run the separately approved runtime test command, ADR governance, and
  `git diff --check`; inspect that only approved runtime, test, spec, and state
  files changed.

### Stop conditions

- Stop if the representation inputs or cache strategy are not yet specified, if
  the proposed fix changes the dual-root public contract, or if it requires an
  unapproved test/CI/build/deploy/environment mechanism change.

## Future Slice B — Markdown fallback escaping and security regression tests

### Scope

- Make fallback markup and content locally controlled.
- Ensure network input and exception details never become interpreted HTML;
  render diagnostics, if retained, only as escaped text.
- Preserve required parsing, safe link handling, sanitization, and fail-closed
  behaviour.
- Add security regression coverage for active markup in Markdown, links, network
  responses, and exception details.
- Leave the CDN/SRI/CSP design question for its human decision checkpoint.

### Expected outputs

- A bounded frontend change to the Markdown rendering/fallback path.
- Regression tests covering missing dependencies, fetch/parse failures, unsafe
  link schemes, raw active markup, and hostile diagnostic strings.
- Evidence that only sanitized output or locally controlled fallback content can
  enter the rendered document.

### Verification

- Inject scripts, event handlers, active/embed elements, unsafe URL schemes, and
  HTML metacharacters through every network/error-controlled input and inspect
  the resulting DOM for executable or injected markup.
- Simulate missing parser, missing sanitizer, fetch failure, and parse failure;
  confirm fail-closed fallback and a safe canonical source link.
- Run the separately approved runtime test command, ADR governance, and
  `git diff --check`; inspect the frontend diff for unrelated presentation
  changes.

### Stop conditions

- Stop if remediation requires deciding CDN hosting, SRI, or CSP posture, changes
  the accepted link policy, or requires an unapproved dependency or
  test/CI/build/deploy/environment mechanism change.

### Expected outputs

- Exercise release API failure, missing assets, stale cache state, fallback or

- Confirm `/trust.json` cannot be interpreted as a signature or independent

### Stop conditions

## Future Slice D — Coherent release resolution and fallback semantics

### Scope

  failure, cache transitions, and unavailable assets without changing the
  accepted authority split.
- Resolve release-backed trust artefacts as one coherent set from one stable
  release identity.
- Never mix release identities or associate fallback bytes with a release or
  verification state not established by resolution.
- Represent unresolved results honestly through the contract produced by Slice
  C and add focused resolution/serving tests.

### Expected outputs

- Approved release-resolution and fallback semantics linked to ADR-0003 and the
  `/trust.json` contract.
- A bounded Worker resolution/response change.
- Tests covering complete releases, incomplete releases, changing release
  indexes, cache hit/miss/failure, unavailable assets, and fallback or degraded
  outcomes.

### Verification

- Assert that every served release-backed artefact and reported release identity
  originates from the same established stable release, or that the response uses
  the specified unknown/degraded/failure state.
- Assert docs and installer remain `saorsa-labs/x0x` `main`-backed and no fork or
  staging authority is introduced.
- Run the separately approved runtime test command, ADR governance, and
  `git diff --check`; inspect network, cache, provenance, and failure paths.

### Stop conditions

- Stop if fallback/failure behaviour is unspecified, if work would change
  upstream authority or the branch/release split, or if it requires a new
  dependency, new network authority, or unapproved
  test/CI/build/deploy/environment mechanism change.

## Future Slice E — Local index and presentation product-claim authority audit

### Scope

- Audit `/llms.txt`, route descriptions, trust/provenance prose, and locally
  maintained frontend claims without treating x0xmd as product authority.
- Map product, protocol, documentation, installer, signed-artefact, and trust
  claims to canonical upstream truth, while identifying serving-layer facts that
  x0xmd legitimately owns.
- Require upstream-derived claims to derive from or cite canonical upstream
  evidence and remain distinguishable from upstream-authored bytes.
- Decide and specify the maintenance evidence needed to keep that mapping
  reviewable and detect drift, without preselecting a generator, build step, or
  other implementation mechanism.
- After the evidence contract is approved, correct bounded unsupported, stale,
  or ambiguously authoritative local claims.

### Expected outputs

- A source/evidence mapping for the audited local claim surfaces, including the
  canonical source, local ownership classification, and drift trigger for each
  claim class.
- An approved maintenance-evidence specification describing how review proves
  derivation, citation, and reconciliation without making x0xmd product
  authority.
- Bounded claim corrections and focused checks only after their source mapping
  and any required mechanism approval are complete.

### Verification

- Review every audited claim against the source/evidence mapping and require
  canonical upstream support or an explicit x0xmd serving-layer classification.
- Exercise drift cases including upstream claim changes, renamed or removed
  documents, changed route descriptions, stale install/trust prose, and
  disagreement between frontend and machine-readable surfaces; confirm the
  specified evidence exposes and reconciles the mismatch.
- Confirm generated or locally maintained indexes remain presentation and
  discovery surfaces rather than independent product, protocol, installer, or
  signed-artefact authority.
- Run only separately approved validation commands, ADR governance, and
  `git diff --check`; inspect any claim corrections for unrelated presentation
  changes.

### Stop conditions

- Stop if a claim correction would change product or upstream authority, if the
  canonical evidence is absent or contradictory, or if work requires choosing
  or changing an unapproved generator, dependency, test harness, build, CI,
  deployment, or environment mechanism.

## Future Slice G — Enforce Worker-first bounded static namespaces

### Prerequisites

- ADR-0005 and ADR-0008 must complete human review and acceptance; no agent may
  accept either record.
- This Proposed plan must receive implementation approval for Slice G.
- The Wrangler routing-precedence change must receive separate explicit
  mechanism-change approval.
- The chosen Cloudflare integration test harness, fixtures, and command must
  receive their own separate explicit mechanism-change approval. Approval of the
  Wrangler change does not imply approval of the test mechanism, or vice versa.

### Scope

- After all prerequisites are met, set `run_worker_first = true` for the
  repository's Workers Assets configuration so `src/index.js` classifies every
  public request before asset delivery.
- Preserve `src/index.js`'s existing classification and delegation: only paths
  in approved `/fonts/*` and `/assets/*` namespaces may reach `env.ASSETS.fetch`.
- Make packaged files outside approved namespaces unreachable and unable to
  shadow root negotiation, exact routes, aliases or redirects, curated
  documents, or the Worker's unknown-path response.
- Add only the separately approved integration harness and control fixtures
  needed to prove Cloudflare routing precedence and shadow resistance.
- Make no unrelated route, response, cache, CORS, authority, or asset-inventory
  change.

### Expected outputs

- The bounded future `run_worker_first = true` Wrangler configuration change.
- Separately approved Cloudflare integration-level precedence tests and control
  fixtures that are demonstrably matchable by the asset mechanism.
- Evidence that Worker classification wins for every non-delegated path while
  approved namespace assets remain deliverable.

### Verification

- Run the separately approved integration command through a Wrangler/Cloudflare
  path that exercises platform asset precedence. Direct `worker.fetch` tests
  alone are insufficient because they bypass the ordering under test.
- Use positive controls to prove that each shadowing fixture is present and
  matchable by the asset mechanism, so Worker-policy results cannot be explained
  by missing or unusable fixtures.
- Verify a present approved `/fonts/*` or `/assets/*` control asset is delivered,
  and a missing path in an approved namespace follows the intended Assets
  not-found behaviour after Worker delegation.
- With matchable controls where applicable, verify a root-level unknown URL is a
  Worker 404; `/` still negotiates browser HTML and CLI installer responses; an
  exact route still returns its Worker response; an alias still applies its
  canonical redirect; and a curated document still follows its Worker route.
- Verify a matchable file in a non-approved nested namespace remains unreachable
  and receives the Worker unknown-path response.
- Run ADR governance and `git diff --check`; inspect the committed diff to
  confirm only the approved Wrangler setting, integration mechanism/fixtures,
  and required evidence/state files changed, with no unrelated route changes.

### Stop conditions

- Stop if ADR-0005 or ADR-0008 is not Accepted, Slice G implementation is not
  approved, either mechanism approval is absent, or the chosen integration path
  cannot distinguish Cloudflare asset precedence from direct Worker invocation.
- Stop if implementation would change `src/index.js` classification/delegation,
  public routes, response semantics, or asset namespaces beyond the bounded
  approved conformance change.
- Stop on any unapproved runtime, test-harness, CI, workflow, build, deployment,
  deploy-action, dependency, or environment expansion.

## Future Slice H — Multi-location Verified Distribution and GitHub-outage Resilience

### Prerequisites and separate approvals

- ADR-0002, ADR-0003, ADR-0004, ADR-0006, and ADR-0009, plus any other ADR
  implicated by the final design, must complete human review and acceptance; no
  agent may accept a record.
- This Proposed plan must receive implementation approval specifically for Slice
  H.
- A concrete delivery, provenance, freshness, degraded-state, and client-
  selection specification must receive separate approval before implementation.
- Before Slice H implementation starts, Slice C's `/trust.json` contract and
  conformance, Slice D's coherent release and fallback semantics, Slice F's
  production configuration and override authority, and Slice G's Worker-first
  bounded static namespaces must each be complete and verified at its own review
  checkpoint. There is no permitted interleaving with unfinished C, D, F, or G
  work.
- Completion and verification of C, D, F, and G require every human, ADR,
  implementation, and mechanism approval already named by those slices. Their
  completion does not approve Slice H or bypass any Slice H approval.
- Current registrar and legal custody of `x0x.md`, and any transfer needed to
  reach the intended Autonomi Foundation stewardship, must be audited from
  evidence. The audit does not itself authorise a transfer or DNS change.
- Any upstream repository, installer, signed-skill, release-process, manifest,
  or other upstream-maintainer change requires separate upstream maintainer
  approval.
- Storage and cache retention; Worker and network behaviour; runtime and
  configuration; deployment mechanism or action; test or CI harness; secrets;
  DNS, registrar, or domain operations; and any new spend each require their own
  explicit approval where implicated.
- One prerequisite or mechanism approval never implies any other approval.
  Push, PR, merge, publish, release, deploy, ADR acceptance, domain operation,
  secret access, and spend remain separately gated actions.

### Scope

- After every prerequisite is met, retain and deliver verified installer and
  release artefact bytes independently through `x0x.md` so approved consumers
  can install and verify x0x while all GitHub delivery hosts are unavailable.
- Ingest only from the canonical upstream and preserve ADR-0003's branch/release
  split. Retain release-backed artefacts as complete coherent sets from one
  established release identity; never assemble cross-release or partially
  verified sets.
- For mutable-`main` installer bytes, expose the immutable canonical source
  revision identity and digest, fetched-at and last-verified-at times, and an
  explicit state of current, last-known verified (stale), or unknown. Current
  requires independently established evidence that the retained revision is the
  canonical upstream `main`; older retained bytes may be offered only as
  last-known verified/stale, never as current or latest. The approved client
  policy must let agents accept or refuse that degraded choice.
- Describe verification with evidence appropriate to the artefact. Installer
  bytes with only canonical revision and hash evidence must not be described as
  signed; signature claims require separately established signature evidence.
- Extend the approved `/trust.json` contract and upstream signed skill provenance
  to expose an extensible set of verified delivery choices, including each
  choice's delivery role, canonical source or release identity, freshness and
  degraded state, and verification relationship. Do not freeze a closed host or
  mechanism list.
- Support policy fixtures for clients that permit raw GitHub delivery, require
  direct `x0x.md` delivery, permit repository access, or impose other approved
  sandbox/security constraints. Client selection must not grant authority to a
  delivery location.
- Preserve canonical `x0x.md` URLs and identity through a serving-backend or
  retained-store migration.
- Preserve inspect-first, download-and-verify, and signature-checking install
  paths where the canonical artefact supplies the applicable evidence, alongside
  the ergonomic canonical command.
- Slice H must not add, change, test as a service, advertise, depend on, or infer
  any redirect, failover, uptime, or compatibility contract for `x0x.sh`.
  Incidental current DNS or HTTP state remains outside scope.

### Expected outputs

- An approved delivery/provenance/freshness/client-selection specification with
  explicit authority; coherent-set semantics; mutable-`main` canonical source
  revision and digest, fetched-at and last-verified-at evidence, and current
  versus last-known-verified/stale versus unknown states; artefact-appropriate
  verification claims; client acceptance/refusal policy; and unresolved-latest,
  degraded, and failure semantics.
- A custody audit based on registrar and legal evidence, with unknowns and any
  transfer need stated without claiming an unperformed operation.
- Separately approved independent storage, ingestion, serving, provenance, and
  client-selection changes bounded to canonical verified delivery.
- Reproducible outage, corruption, coherence, sandbox-policy, and backend-
  migration evidence from the separately approved harness.

### Verification

- In fresh disposable environments, deny every GitHub-owned delivery host,
  including API, raw-content, repository, redirect, and release-object hosts.
  Capture request logs that prove installation and verification completed without
  an attempted or successful GitHub escape.
- Clear transient Worker, CDN, resolver, and client caches while retaining only
  the separately approved independent store; repeat GitHub-blocked installation
  and artefact retrieval through stable `x0x.md` URLs.
- Fetch the same canonical installer and release artefacts through multiple
  advertised locations and compare bytes, hashes, and source identity, plus
  signatures, manifests, provenance, and release identity where applicable to
  that artefact. Do not require or claim an installer signature when only
  canonical revision and hash evidence exists.
- Inject corrupt bytes, bad or mismatched signatures, altered manifests, missing
  members, partial retained sets, and cross-release combinations; require
  fail-closed rejection or the exact approved degraded/failure response without
  serving an unverifiable combination.
- Make latest-release resolution unavailable or ambiguous and confirm the system
  reports unresolved latest honestly rather than relabelling retained or mixed
  bytes as the latest release.
- Use a non-tautological mutable-`main` fixture whose upstream state and expected
  immutable identities are established independently of the system under test:
  establish upstream `main` at revision A, retain A with its canonical digest and
  fetched/last-verified evidence, advance upstream `main` to independently known
  revision B, then deny all GitHub access before `x0x.md` can refresh. Prove
  retained A is never labelled current or latest, still carries A's revision,
  digest, and last-verification evidence, and is exposed only under the approved
  last-known-verified/stale semantics. Exercise policy fixtures that accept A and
  refuse A in that state. Restore access, refresh and verify B, and prove later
  retrieval does not silently downgrade from B to A.
- Exercise sandbox-policy fixtures that independently allow and deny raw GitHub,
  direct `x0x.md`, repository access, and other specified choices; require the
  client to select only an allowed verified option without changing authority.
- Swap the approved delivery backend or retained store while preserving stable
  public URLs, coherent canonical identity, verification metadata, and the
  specified freshness/degraded behaviour.
- Verify the signed upstream skill and machine-readable provenance each expose
  plural, extensible verified delivery options with accurate role, identity,
  freshness, and verification relationships.
- Inspect Slice H changes and dependency paths to confirm they do not add, change,
  advertise, depend on, or infer a redirect, failover, uptime, or compatibility
  contract for `x0x.sh`. Do not request or test `x0x.sh` as a service, and make no
  assertion about its incidental DNS or HTTP state.

### Stop conditions

- Stop if any applicable ADR is not Accepted, Slice H is not approved, the

- Stop if freshness, unresolved-latest, degraded, partial-set, or failure

before it is marked Done; run clean-context review when the affected behaviour
or operational evidence is complete enough to exercise. Slice E review must

divergence, and the next attended checkpoint.
